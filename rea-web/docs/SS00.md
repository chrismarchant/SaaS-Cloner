# SS00 — REA Web + Build Recovery: system specification

Status: G00 baseline document. Owner: architecture lead. Supersedes the
blueprint's model allocation and execution instructions; the blueprint remains
the initial architecture reference.

## 1. Mission

Extend the upstream REA reverse-engineering CLI/MCP server (pinned in
[UPSTREAM-PROVENANCE.md](UPSTREAM-PROVENANCE.md)) with a web control plane that
supports two workflows without altering upstream behaviour:

1. **Investigate** — reverse-engineer supplied binaries, applications, packages,
   websites and runtime captures through upstream REA, producing evidence-backed
   findings and reconstruction obligations.
2. **Preserve & restore** — capture the operator's own builds (source, deps,
   data, assets, infrastructure, integrations, product documentation,
   verification evidence) into a portable, independently restorable recovery
   package, and verify clean restoration.

Upstream CLI, MCP server, providers, skills, docs and tests remain available and
unchanged; the extension consumes upstream through its public MCP boundary
(primary) and CLI (where a verified workflow needs it).

## 2. Non-negotiable invariants

- **Upstream preservation.** No file outside `rea-web/` is modified. Verified by
  `git diff upstream-baseline...HEAD -- . ':(exclude)rea-web'` being empty and
  by re-running the upstream deterministic gate at every checkpoint.
- **No invented inventory.** Tool, provider, prompt and CLI inventories are
  discovered from the pinned catalog (`.cache/mcp-tool-catalog.json`,
  `docs/public/product-catalog.json`) and from the live runtime (`tools/list`,
  `binary_session`). Counts are computed, never hardcoded.
- **Epistemic separation.** Every finding is labelled observed fact, inference,
  reconstruction proposal, or unknown. Upstream `normalized_result`,
  `raw_result`, `limitations`, `coverage` and `residual_unknowns` are preserved
  verbatim alongside any derived summary.
- **Isolation.** One upstream MCP process and workspace per investigation; no
  active-target or evidence-ledger state crosses investigations or users.
  Retained `evidence_id`s are bound to their owning upstream session; follow-up
  calls route to that session. Portable evidence is exported before teardown.
- **Visible unavailability.** Unavailable capabilities carry upstream's own
  `reason`/`remediation`; the extension never silently switches providers.
- **Control plane ≠ execution plane.** Supplied targets execute only on runners,
  never in the API process; runners hold no control-plane database or object
  store credentials beyond their scoped runner token.
- **Durable jobs.** Explicit state machine, leases with fencing tokens,
  idempotency keys, persisted event sequence numbers, resumable SSE, budgets,
  and cleanup records.
- **Secrets.** Default exports contain secret names/references, never values.
  Credentials never reach browser bundles, archives, logs, or model inputs.
- **Honest verification.** Status vocabulary is `captured`,
  `integrity_verified`, `clean_build_verified`, `data_restore_verified`,
  `behavior_verified`, `partial`, `blocked`. No completeness percentages.

## 3. System context

```
Browser (React SPA)
  │  HTTPS, cookie session or bearer token
  ▼
Application API (Fastify, OpenAPI 3.1, SSE)  ──►  PostgreSQL (metadata, jobs, leases, events)
  │                                            ──►  Object storage (S3-compatible; fs backend for local)
  │  runner protocol (HTTPS, runner token, outbound-only from runner)
  ▼
Runner (Linux/macOS/Windows/device host)
  ├─ workspace per job (private dir, quotas)
  ├─ upstream REA MCP process per investigation  (stdio)
  ├─ upstream REA CLI for verified one-shot workflows
  ├─ preservation collectors (git, package managers, pg_dump, object listing, infra, Code-to-PRD)
  └─ standalone recovery verifier (same binary as the offline CLI)
  │
  ▼  (server-side, never from browser)
Model connector (configurable provider; disabled when unconfigured)
```

Railway hosts the API, the web app, PostgreSQL and (optionally) a Linux runner
for capabilities that need only Node + bring-your-own Linux tools. Capabilities
requiring macOS, Windows, GUI, devices, Docker-in-Docker or privileged
execution are routed to self-hosted runners; the capability panel shows why.
Railway's execution environment is not assumed: each runner proves its
capabilities at registration (see §7).

## 6. Job state machine

States: `queued`, `preparing`, `running`, `awaiting_approval`, `succeeded`,
`failed`, `cancelled`, `interrupted`.

| From                | To                                                | Trigger                                                                                       |
| ------------------- | ------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `queued`            | `preparing`                                       | runner claims lease (fencing token issued)                                                    |
| `queued`            | `cancelled`                                       | user cancel                                                                                   |
| `preparing`         | `running`, `failed`, `cancelled`, `interrupted`   | runner progress / failure / cancel / lease expiry                                             |
| `running`           | `awaiting_approval`                               | policy requires approval for a requested effect                                               |
| `running`           | `succeeded`, `failed`, `cancelled`, `interrupted` | runner completion (fenced) / cancel / lease expiry                                            |
| `awaiting_approval` | `running`                                         | approver grants                                                                               |
| `awaiting_approval` | `cancelled`                                       | approver rejects, or approval deadline passes                                                 |
| `awaiting_approval` | `interrupted`                                     | lease expiry                                                                                  |
| `interrupted`       | `queued`                                          | retry policy permits and effect ledger shows no non-repeatable effect in flight; attempt += 1 |
| `interrupted`       | `failed`                                          | retries exhausted or non-repeatable effect ambiguous                                          |

Terminal: `succeeded`, `failed`, `cancelled`. Every transition appends a
`job_event` with a per-job `seq`. Runner-originated transitions carry the
lease's `fencing_token`; a token that is not the job's current token, or a lease
past `expires_at`, is rejected with `409 stale_lease` and recorded as an event.
Cancellation sends `cancel` to the owning runner, which terminates the owned
process group (upstream `close_binary` first, then SIGTERM/SIGKILL escalation),
records cleanup (`cleanup_complete` | `cleanup_incomplete` with owned resource
kinds), and reports. Restart behaviour: the API reaper marks jobs with expired
leases `interrupted`; the runner, on restart, discards workspaces of jobs it no
longer holds.

Budgets (per job, enforced by runner, reported to API): `wall_ms`, `cpu_ms`,
`memory_bytes`, `disk_bytes`, `tool_calls`, `model_input_tokens`,
`model_output_tokens`, `artifact_bytes`. Counted budgets the runner spends
itself (`tool_calls`, model tokens) stop further work at the limit: planned
steps are skipped with a `budget_exhausted` finding and the job completes with
`result.partial: true`. Measured budgets (`wall_ms`, `cpu_ms`,
`memory_bytes`, `disk_bytes`, `artifact_bytes`) abort the job when exceeded and
fail it with `budget_exceeded` naming the dimension.

## 7. Runner contract

Registration (`POST /runners/register`, runner token) sends a capability
report. Nothing is trusted as present unless the runner proves it:

```
capabilities = {
  host: { os, arch, hostname_hash, kernel, docker_available: bool, gui: bool, adb_devices: n },
  rea: { package_version, root_path_hash, build_commit|null, source_sha (git rev-parse of runner's REA checkout, if any),
         sdk: {server, core}, catalog: {counts, digests}, skill: {name, expected_version} },
  tools_list: [{ name, title, annotations, has_output_schema, input_schema_sha256 }],   // from tools/list
  tool_availability: binary_session.result.tool_availability,                            // verbatim
  analysis_provider_candidates: binary_session.result.analysis_provider_candidates,      // verbatim
  provider_capabilities: binary_session.result.capabilities,                             // verbatim
  env_capability_names: [ "GHIDRA_INSTALL_DIR", ... ],   // names of REA_* / provider env vars that are SET; never values
  labels: [...], max_concurrent_jobs, workspace_root_free_bytes
}
```

Jobs declare `requirements = { tools: [names], providers: [ids], os: [..],
labels: [..], effects: [..] }`. The orchestrator offers a job only to runners
whose live report satisfies it; the UI's capability panel renders the unmet
reasons using the runner's `reason` and `remediation` strings.

Runners connect outbound only (long-poll `POST /runners/{id}/claim`, heartbeat
`POST /runners/{id}/heartbeat`, events `POST /jobs/{id}/events`, completion
`POST /jobs/{id}/complete`, all carrying the fencing token). No inbound ports,
no exposed CDP/ADB/MCP endpoints.

## 8. REA adapter contract

- Boundary: upstream MCP over stdio using `@modelcontextprotocol/client@2.3.1`
  (same pinned SDK as upstream's server). CLI (`scripts/rea.mjs`) is used for
  evidence import/inspect of exported bundles and one-shot commands whose
  workflow is documented upstream as CLI-only.
- Per-investigation: fresh process, `cwd` = private workspace, environment
  snapshot limited to an allowlist (`PATH`, `HOME` (private), `REA_*` provider
  locators the runner is configured to pass, `TMPDIR` (private)), `REA_LOG_LEVEL`
  set by policy. Process group owned; killed on teardown.
- Startup discovery: `tools/list` (paged), `prompts/list`, `binary_session {}`.
  Recorded per session: package version, server identity, SDK, protocol,
  catalog digests, availability groups, candidates, client features.
- Every `tools/call`: arguments validated against the live advertised
  `inputSchema` before dispatch; effects/annotations consulted against policy;
  progress token supplied; cancellation wired to the job's abort signal;
  result stored raw (full `content`, `structuredContent`, `isError`) in object
  storage and summarised (`evidence_id`, `normalized_result` keys, limitations,
  coverage, residual unknowns) in `tool_call.derived`.
- Retained references (`{"kind":"retained-evidence","evidence_id":...}`) are
  valid only within the owning session; the adapter maps `evidence_id →
  session_id` and refuses cross-session use with an explicit error.
- Before teardown: `export_evidence_bundle` to a workspace path, uploaded as an
  `evidence_artifact`; then `close_binary`; then process-group termination; the
  cleanup result is recorded.
- Summaries never replace raw outputs; the UI's evidence panel renders both.

## 9. Investigation workflow

1. Select target (upload, URL, runtime capture file, or runner-local path that
   the runner itself registered from its allowlist).
2. Define the question/feature.
3. Routing: the runner classifies the target (extension, magic bytes,
   directory/ASAR shape) using a route table transcribed from the upstream
   skill's "Route the target first" section and the live `tool_availability`;
   the UI shows the chosen first tool, required providers, and which runners
   can satisfy them.
4. Execution policy: `static_only` (default) or `static_plus_runtime`;
   allowed effect set; approval-required effect set (default: any tool whose
   effects include `executesForeignCode`, `mutatesDevice`, `mayDiscardData`, or
   `accessesNetwork`); tool-call and model budgets.
5. Run: deterministic first pass (routing tool + `binary_session` +
   evidence-safe follow-ups), then a bounded model-driven follow-up loop when a
   model provider is configured (otherwise recorded as unavailable).
6. Findings: facts (from `normalized_result`), inferences (upstream-marked
   inferred evidence or model-attributed with citation), proposals (from
   `build_reconstruction_obligation_ledger` and model), unknowns (from
   `list_unknowns`/`record_unknown` and unmet capabilities).
7. Export: evidence bundle, raw results, findings, obligations; downloadable
   as a zip whose index lists sha256 for each member.

UI surfaces: targets list, capability panel, investigation timeline (job
events + tool calls), feature/relationship view (application graph when the
producer supplies one), evidence detail (raw + derived), version comparison
(`compare_*` tools over two retained/inline evidence records), export screen,
and a schema-generated advanced tool form for every advertised tool.

## 10. Preserve & restore workflow

Plan → capture → package → verify → export.

- **Plan** (runner job `preservation.plan`): enumerate components reachable
  from the build's declared source and connections; check permissions (read
  access to repo, DB role privileges, bucket listing); record dependencies
  (lockfiles, runtimes, images), consistency strategy (DB snapshot method and
  whether assets are captured within the same window), and known omissions
  (e.g., private registries without credentials, Supabase Auth settings that
  require manual export).
- **Capture** (`preservation.capture`): collectors write into a staging
  package; each file hashed; manifest records timestamps per component.
- **Package**: manifest v1 (see [RECOVERY-FORMAT.md](RECOVERY-FORMAT.md)),
  payload directories, `RECOVERY.md`, restore scripts, embedded verifier.
- **Verify** (`recovery.verify`): the standalone verifier runs in a disposable
  workspace with production endpoints blocked, schedules/webhooks disabled,
  and test credentials; results recorded per scope.
- **Export**: tar of the package with optional detached signature and optional
  encryption; keys never inside the archive.

Collectors at G03: Git (history/refs/submodules/LFS pointers), dependency
lockfiles and toolchain versions, PostgreSQL (`pg_dump` custom format +
globals), filesystem/object assets with manifests, infrastructure descriptor
(declared services, commands, health checks, env var names, domains,
schedules), integrations descriptor, product documentation via Code-to-PRD
(stdlib Python subprocess) plus REA shipped-artifact evidence where configured.
Supabase specifics: database backup via `pg_dump`; Auth, Storage objects, Edge
Functions, platform settings and external OAuth config are recorded as separate
components with their own status (captured | blocked | manual).

## 11. Model connector

Server-side only. `REA_WEB_MODEL_PROVIDER ∈ {disabled, scripted, anthropic}`.
`anthropic` uses `REA_WEB_ANTHROPIC_API_KEY`, `REA_WEB_MODEL_ID`,
`REA_WEB_MODEL_MAX_OUTPUT_TOKENS`. The connector exposes
`complete(request, signal)` returning content blocks, `stop_reason`, and usage;
tool definitions are the live advertised schemas; every proposed tool call is
validated against the schema and the policy before execution; usage is
accounted against the job budget; cancellation aborts in-flight requests; a
missing credential yields `model_unavailable: not_configured` and the
investigation proceeds without the follow-up loop. The development session's
model has no relationship with runtime availability.

## 12. Security posture (summary; details in THREAT-MODEL.md)

- Authorization on every project-scoped route, stream, and runner action.
- Uploads: size caps, magic sniffing, archive bomb limits (entry count,
  ratio, total expanded bytes), path traversal and symlink rejection during
  extraction, no execution in the API process.
- URL targets: scheme allowlist (http/https), resolve-then-connect against
  private/link-local/loopback ranges, redirect re-validation, DNS rebinding
  guard by pinning the resolved address for the connection.
- Child processes: `spawn` with argument arrays only; private env allowlist;
  process groups; timeouts; rusage accounting.
- Logs: structured, with redaction of configured secret names, bearer tokens,
  cookies, and `Authorization` headers.
- Model inputs: redaction pass over any text that leaves the runner.
